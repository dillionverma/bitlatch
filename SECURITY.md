# Security and current boundaries

Latch 0.1 is a private prototype, not an audited password manager.

## Implemented boundaries

- The official Bitwarden CLI performs authentication, password derivation, encryption, decryption, and sync. Production code contains no custom vault cryptography.
- Latch supplies a separate `BITWARDENCLI_APPDATA_DIR` within its application data. This requires the installed CLI to honor the path. During the design pass, the discovered Nix CLI reported an existing locked account despite a new data directory; the cause remains unresolved. Do not treat isolation on that installation as verified.
- The master password and session key are supplied through the child-process environment, not command arguments or logs. The vault server receives the session key the same way. Unlocking is done by the vault server rather than a second CLI, so there the master password travels over the private socket pair as a request body; it still never reaches a command line, a log, or anything outside that one process. New/edited item data goes through stdin. The session key is held in memory and discarded at lock. The CLI's own encrypted cache and authentication state remain on disk.
- Searchable item metadata and selected supported secrets are cached in the main process while unlocked. The renderer gets summaries and explicitly selected details. The website gets only the selected username and password.
- Browser requests use native messaging, then a Unix socket with owner-only permissions and a random pairing token. Only the pinned extension origin is allowed by the native host manifest. The browser never reaches the vault server described below.
- Vault reads and writes go to an unlocked `bw serve` process that Latch keeps running while the vault is open. It is given one end of a connected socket pair as a file descriptor, so it listens on no port and leaves no socket file on disk, and no other process on the machine can reach it. Its own origin and Host checks stay on. Commands that change which account is signed in stop the server and run one-shot.
- Browser code derives the URL from trusted sender metadata, rejects cross-origin frames, and re-checks URL matching immediately before returning a selected credential. Server connections always require HTTPS.
- Filling requires HTTPS, except on loopback and the local network (10/8, 172.16/12, 192.168/16, 169.254/16 and `.local` names), where a certificate is not possible and the password does not leave the network. Routers and other local devices are reachable this way; a plain HTTP site on the internet is never filled. Saving an address is not restricted, so an item may hold a URL that Latch will not fill.
- Regex URI rules, shared organization items, and master-password-reprompt items fail closed in this MVP. Logins and secure notes can be edited; every other item type and any passkey-bearing item is read-only. Items already in the trash are excluded.
- Deleting asks for confirmation and moves the item to Bitwarden's trash, which Latch can browse and restore from. Latch never deletes permanently, and refuses to delete shared, reprompt-protected or passkey-bearing items. A trashed item cannot be edited and is never offered to a browser for filling.
- An unset/default URI match uses the exact host and port. Only an explicit base-domain rule includes sibling subdomains; client-wide matching preferences are not exposed by the CLI. This may show fewer suggestions than the official extension.
- Lock clears Latch's cache, cancels CLI operations, stops the vault server and its decrypted copy of the vault, invalidates pending reads, clears the renderer, and clears the clipboard if it still contains the copied value. Quitting does the same. Screen lock/sleep also locks the vault; idle timeout is five minutes.
- Touch ID unlock is off by default. Turning it on keeps the CLI session key on this Mac, encrypted with Electron's `safeStorage`, whose key lives in the login Keychain. Two honest limits: `bw lock` destroys a session key outright, so while this is on Latch does **not** lock the CLI and the stored key is what guards the vault instead of the master password; and the Touch ID prompt is a gate Latch chooses to honour, not one macOS enforces on the stored bytes, because Electron cannot request a biometry-guarded Keychain entry. The master password still works, and the key is forgotten when Touch ID is switched off or the account is signed out.
- A sign-in seen in the browser is only offered for saving while the vault is unlocked, so a captured password never outlives the lock meant to clear it. The offer is held in memory for three minutes, is only ever returned to the origin it came from, and is written only after a real click on the prompt. Latch checks whether the password differs from the stored one, so an unchanged sign-in prompts nothing.
- Native appearance uses a separate, validated read/subscription interface. It exposes only material, activity, theme and accessibility flags. Solid is the default; optional native material is visible only behind navigation. Credential panes, auth, dialogs and browser UI remain opaque.
- Electron uses a sandboxed renderer, context isolation, no Node integration, a restrictive Content Security Policy, denied web permissions/navigation/new windows, and a small validated IPC interface.

## Limits

- Processes running as the same macOS user can inspect process memory/environments or impersonate local software. This is not a defense against a compromised Mac. JavaScript garbage collection does not guarantee immediate secret zeroization.
- Filling intentionally exposes the chosen password to the destination page. Page-load filling is opt-in per origin, only with one matching account, and does not submit forms.
- Browser lock status is request/response based. Visible offers clear at the next status response (normally a one-second poll plus bridge latency); instant push clearing and lock/unlock between polls are not guaranteed. The backend still rejects locked reads and commits. Offers have no unique identifier, so identical-metadata replacement offers are not distinguished by the UI.
- Inline page UI is not a browser-owned trusted surface. Sites may obscure or imitate it. The matching and secret-release decisions remain outside page JavaScript.
- This is a limited field detector: complex pages, closed shadow DOM forms, unusual multi-step flows, and accessibility-only controls are not guaranteed. Signup/password-change forms are refused.
- No passkey provider, SSO flow, system-wide autofill, enterprise policy engine, or full vault feature parity. Touch ID and browser save/update offers are implemented; native biometric success and production-account behavior remain unverified in this design pass.
- Editing performs a pre-write sync and revision check. This reduces stale edits; it is not a general offline conflict-resolution engine. Passkey-bearing, shared, and reprompt-protected items cannot be edited.
- The current local package skips signing and fails strict signature verification. The older private release had local ad-hoc signing. Neither is Developer ID notarized. Browser installation uses Developer mode.
- Cloud account flows depend on Bitwarden's authentication policy. Two-step and new-device codes are typed into the official CLI's own prompt; Latch keeps the master password in main-process memory only until that sign-in finishes, so it can restart the CLI with the chosen method or after a rejected code. Methods the CLI cannot complete (WebAuthn security keys, Duo, SSO) require personal API-key sign-in followed by master-password unlock. No production account was unlocked and no personal vault items were read in this design verification. One startup exposed an existing account identity despite the requested isolated path; its capture was removed and all later appearance checks used a synthetic CLI.

Please report potential vulnerabilities privately to the repository owner. Do not include credentials or vault exports in issues.
