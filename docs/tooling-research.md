# Latch tooling research

Researched 2026-09-24. External research only; recommendations below are judgments, not an implementation plan or a verified migration. Local reads covered repository instructions, package metadata, working-tree status, and installed electron-builder hook ordering. No installs, builds, tests, signing, or releases were performed.

## Recommendation and tradeoffs

**Prefer a small pnpm workspace: three apps (desktop, browser, Raycast) plus one shared package, while keeping `vp pack` initially.** One install/lockfile can coexist with independent manifests, configs, and release artifacts. Keep shared limited to existing runtime-neutral contracts/utilities; do not add a separate library build unless consumers need it. Adopt electron-vite only if replacing development/watch/start glue provides a concrete reduction in maintenance. This is a design recommendation based on [pnpm's workspace model](https://pnpm.io/workspaces) and [WXT's project boundaries](https://wxt.dev/guide/essentials/project-structure).

| Choice                           | Benefit                                                                                 | Cost / qualification                                                                                             |
| -------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Keep one desktop/browser package | Fewest paths and manifests; shared source imports stay simple                           | Coupled dependencies, metadata, generated TypeScript settings, and Firefox source archive scope                  |
| Small pnpm workspace             | One install and lockfile; each product owns dependencies, scripts, assets, and metadata | Shared-source packaging and desktop runtime dependency collection must remain correct                            |
| Keep Vite+ / `vp pack`           | Lowest migration risk; already covers JS bundling and renderer builds                   | Explicit responsibility for process isolation, Electron startup/reload, and packaging orchestration              |
| Adopt electron-vite for desktop  | Conventional main/preload/renderer config and Electron development lifecycle            | Another integration/version boundary; native host, Swift extensions, and signing still require explicit handling |

The table is an inference from the guidance below, not a claim that either layout is required. Avoid introducing Turbo/Nx or a publishable shared-library build solely to have a monorepo.

## Build conventions and version boundaries

- **Vite vs Vite+:** Vite's production build starts from HTML for a web application. Vite+ distinguishes `vp build` for applications from `vp pack` (tsdown) for libraries/standalone artifacts, with `pack` configured in `vite.config.ts`. The existing renderer/build split is therefore reasonable; `vp pack` is not an Electron installer or Apple extension builder. [Vite build](https://vite.dev/guide/build), [Vite+ pack](https://viteplus.dev/guide/pack).
- **Alias discipline:** official Vite+ migration rules use `vite → npm:@voidzero-dev/vite-plus-core` and align its version with `vite-plus`; shared overrides can affect other Vite consumers. Latch declares both at `1.0.0-rc.0`. Keep those pins aligned, but do not infer that WXT or electron-vite is certified against that alias merely because installation succeeds. [Migration rules](https://viteplus.dev/guide/migrate-rules), [upgrade guidance](https://viteplus.dev/guide/upgrade-project).
- **electron-vite:** one `electron.vite.config.ts` describes `main`, `preload`, and `renderer`; `dev` builds Node-side code, starts the renderer server, and launches Electron. It can replace substantial watch/start glue if that is the actual maintenance problem. Current docs identify v5; dependency externalization is built in via `build.externalizeDeps`, replacing the older plugin. The inspected v5.0.0 manifest declares Vite 5/6/7 peers, not Vite+. Compatibility with Latch's RC core remains unverified. [CLI](https://electron-vite.org/guide/cli), [v5 migration](https://electron-vite.org/guide/migration), [versioned manifest](https://github.com/alex8088/electron-vite/blob/v5.0.0/package.json).
- **WXT owns extension build configuration:** customize its internal Vite through `wxt.config.ts`'s `vite` callback. WXT advises retaining its build defaults and warns that some Vite plugins behave differently under its orchestration. Sharing dependencies does not require sharing renderer build options. [WXT Vite configuration](https://wxt.dev/guide/essentials/config/vite).
- **Version caveat:** local declarations are Electron `44.4.1`, electron-builder `^26.8.1`, WXT `^0.21.4`, and pnpm `11.25.0`; ranges are not installed-version evidence. The installed `electron-builder` and `app-builder-lib` were independently verified as **26.15.3**. WXT docs display 0.21.4, whereas current pnpm docs display 12.x (the attempted 11.x URL redirects). electron-builder's current docs describe v27, including signing keys moved under `mac.sign`; use its **v26 docs** for Latch, not v27 snippets. No upgrade is recommended as part of cleanup. [builder migration](https://www.electron.build/docs/migration/v26-to-v27/), [v26 macOS reference](https://www.electron.build/v26/docs/mac/), [pnpm docs](https://pnpm.io/workspaces).

## Preload and native-host boundaries

**Keep sandboxed preload a self-contained CJS-compatible artifact.** Electron says sandboxed preload cannot use ESM imports, and its restricted `require` cannot load arbitrary local files. A CJS filename alone does not establish safety: shared chunks, dynamic imports, or externalized npm dependencies can still break it. Keep `contextIsolation` and sandboxing; change bundling rather than weakening the runtime boundary. [Electron ESM](https://www.electronjs.org/docs/latest/tutorial/esm), [Electron sandbox source](https://github.com/electron/electron/blob/main/docs/tutorial/sandbox.md).

electron-vite v5 defaults to externalizing production dependencies for main/preload. Its guidance for sandbox preload is `externalizeDeps: false`; multiple preload entries additionally need `isolatedEntries: true`, currently documented as **experimental**. Native addons remain external. For `vp pack`, use independent build configurations when necessary to guarantee preload cannot acquire a shared chunk from main/native-host. This last sentence is a recommendation, not a verified RC-specific flag recipe. [Dependency handling](https://electron-vite.org/guide/dependency-handling), [isolated builds](https://electron-vite.org/guide/isolated-build).

**Native messaging host is a separate executable contract, not a preload.** Chrome launches the registered host and exchanges length-prefixed JSON over stdin/stdout. Build for its actual runtime, preserve a deployable executable/launcher and registration path, keep diagnostics off protocol stdout, and avoid importing desktop startup code. A single-file host is a useful simplification, not a browser requirement. Its own dependency graph may use Node APIs that preload cannot. [Chrome native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging).

There is documentation drift: electron-vite's sandbox explanation lists older Node polyfills; Electron's current source documents a narrower surface. Consult the Electron version actually shipped before relying on a particular builtin.

## Workspace and packaging implications

pnpm workspaces require `pnpm-workspace.yaml`; the shared lockfile defaults on, and `workspace:*` requires a local dependency rather than silently selecting a registry package. Preserve package-local dependency declarations even with a common install. Raycast should retain its extension manifest and `ray` commands executed in that package's directory. Its official CLI guidance does not itself establish a pnpm-workspace compatibility guarantee. [pnpm workspaces](https://pnpm.io/workspaces), [Raycast CLI](https://developers.raycast.com/information/developer-tools/cli).

electron-builder supports a single package and an optional separate application package; splitting packages is not necessary merely because native dependencies exist. It excludes development dependencies from runtime dependency copying and provides `install-app-deps` for Electron-native dependency alignment. Consequently, declare external desktop runtime dependencies with desktop; browser/Raycast dependencies should not become desktop shipping dependencies accidentally. [builder v26 overview](https://www.electron.build/v26/docs/).

**Do not prescribe hoisting from old tutorials.** Electron's introductory guide recommends pnpm hoisting for its packaging-tool assumptions, while current electron-builder source has a pnpm-specific collector handling isolated/hoisted layouts and pnpm 11 workspace output. That source is moving master, not proof for Latch's installed v26 patch. Preserve the current linker until the parent's audit establishes the exact collector behavior; workspace migration needs a packaged-app dependency check, especially for native modules. [Electron tutorial source](https://github.com/electron/electron/blob/main/docs/tutorial/tutorial-2-first-app.md), [builder collector source](https://github.com/electron-userland/electron-builder/blob/master/packages/app-builder-lib/src/node-module-collector/pnpmNodeModulesCollector.ts).

## macOS extensions, signing, and notarization

1. **Stage before signing:** electron-builder runs `afterPack` after app files/resources are copied but before signing; `afterSign` follows signing and precedes distributable creation. Recommendation: compile native targets separately, embed final `.appex` contents in the pre-sign phase, then sign. Do not mutate embedded resources after the outer signature. [v26 build lifecycle](https://www.electron.build/v26/docs/features/build-lifecycle/).
2. **Sign inside out with per-target settings:** Apple explicitly treats `.appex` as a main executable, signs it before the containing app, and warns against `codesign --deep` for signing. Restricted entitlement claims require suitable distribution profiles; app and extension may each need their own profile. A common Electron `entitlementsInherit` file is not a substitute for checking each AutoFill/Safari target. [Apple distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/), [provisioning model](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles).
3. **Choose one signing owner:** v26 offers custom `mac.sign` and `signIgnore` regexes. Pre-signing an extension then excluding it from builder signing is viable only if that step fully signs it and the enclosing signature is applied afterward. `signIgnore` is not a way to ship unsigned code. This is an inference from Apple's ordering and builder's documented controls. [v26 mac options](https://www.electron.build/v26/docs/mac/).
4. **Choose one notarization owner:** v26 already integrates `@electron/notarize` with supported credentials; a custom post-sign workflow should be justified by an unmet need. Developer ID signatures, hardened runtime, timestamps, and all nested executables matter. Notarization acceptance does not establish that AutoFill/Safari registration or entitlement-dependent behavior works on another Mac. [v26 notarization options](https://www.electron.build/v26/docs/mac/#notarize), [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

WXT generates Safari web assets but does not create/publish the native wrapper. Apple packaging consumes the built Safari output, not the source tree. Retaining a focused native build stage is therefore justified; whether handbuilt Swift targets or Xcode targets are simpler depends on the parent's local audit. [WXT Safari publishing](https://wxt.dev/guide/essentials/publishing#safari).

**Exact v26.15.3 hook check:** installed `app-builder-lib/out/platformPackager.js` copies extra files/resources, emits `afterPack`, applies fuses, then calls signing and `afterSign`. Its `out/macPackager.js` calls built-in notarization inside the non-MAS signing path, **before `afterSign`**. Therefore, moving extension assembly/re-signing to `afterSign` can be too late when built-in notarization is enabled. Keep native compilation/embedding and target-specific signing responsibilities; remove a custom notarization script only after confirming built-in authentication, submission/stapling, and failure behavior cover its work. Hook invocation alone is not signature verification. These installed-source observations refine the [v26 lifecycle](https://www.electron.build/v26/docs/features/build-lifecycle/) and [hook reference](https://www.electron.build/v26/docs/features/hooks/); they are not claims about every v26 patch or v27.

## WXT output, browsers, icons, and source archives

- Prefer standard `.output/<browser>-mv<version>` artifacts and generated `.wxt` TypeScript config unless a consumer requires different paths. `srcDir` is configurable; `public/` stays relative to project root by default. Avoid a shared output directory whose clean step can erase another target. [Project structure](https://wxt.dev/guide/essentials/project-structure), [manifest output](https://wxt.dev/guide/essentials/config/manifest).
- `-b` selects a browser; current defaults are Chrome/MV3 and Firefox/Safari/MV2. Preserve explicit `--mv3` for Firefox when intended. WXT supports per-browser manifests/entrypoint filtering, but API/permission compatibility remains application work. [Browser targeting](https://wxt.dev/guide/essentials/target-different-browsers).
- Standard PNG names such as `public/icon-16.png` or `public/icon/16.png` populate manifest icons automatically; `@wxt-dev/auto-icons` can generate sizes. Prefer conventions over handwritten copying if branding inputs fit. Desktop ICNS and Raycast assets still have separate consumers. [Manifest/icons](https://wxt.dev/guide/essentials/config/manifest).
- Use `wxt zip` per required target; Edge can reuse Chrome's archive unless Edge-specific behavior differs. Firefox zip also emits a sources archive. Explicitly review its contents and rebuild from extraction: a workspace archive must include needed shared source, manifests, lockfile/config, and reproducible instructions without unrelated private/native files or secrets. A separate browser package narrows scope but does not automatically make `workspace:` dependencies reconstructible. [Publishing/source ZIP guidance](https://wxt.dev/guide/essentials/publishing).

## Remaining decisions for the local audit

Determine whether Electron dev orchestration actually merits electron-vite, whether each preload/host output is independently loadable, which installed builder collector handles pnpm 11, and who signs/notarizes each native target. Any later migration should preserve those contracts and verify packaged startup plus reconstructed Firefox sources. This research establishes conventions and caveats, not working compatibility or release readiness.
